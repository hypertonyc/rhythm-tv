# Сервер

Качает торрент по запросу, перекодирует нужный эпизод в HLS через ffmpeg
и отдаёт плейлисты клиенту на телевизоре. На `/` лежит встроенный веб-клиент —
тот же плеер в браузере (удобно для отладки без телевизора) и, главное,
единственное место, откуда управляют библиотекой торрентов.

Торрентов на сервере лежит сколько угодно, но **активен ровно один**: его серии
видит телевизор, и на него работает единственный сеанс перекодирования. Новый
`.torrent` загружают со страницы (в том числе с телефона), там же переключают
активный — телевизор подхватывает смену сам, без перезапуска и без деплоя.

Go, из зависимостей — `github.com/anacrolix/torrent`; ffmpeg и ffprobe вызываются
процессами. Раскладка пакетов и то, зачем разрезано именно так, — в
[CLAUDE.md](../CLAUDE.md).

Рядом лежит [legacy/server.mjs](legacy/server.mjs) — прежний сервер на Node.
Он не собирается в прод и остаётся эталоном для сверки: контракт с телевизором
заморожен, и [scripts/compat-node-vs-go.sh](../scripts/compat-node-vs-go.sh)
поднимает оба сервера на одном торренте и сравнивает ответы.

## Запуск

В Docker (образ ставит ffmpeg сам):

```sh
docker build -t torrent-media-server .
docker run --rm -p 8000:8000 -v /path/to/torrents:/data torrent-media-server /data/file.torrent
```

Локально — нужны Go 1.26 и ffmpeg в `PATH`:

```sh
go run . /path/to/file.torrent
```

Путь к `.torrent` — необязательный аргумент: это seed, он включается при первом
запуске, пока выбор не сделан. Дальше активный торрент помнится в
`<TORRENT_LIB>/.tms-active` и меняется со страницы. Без аргумента нужен
`TORRENT_LIB`:

```sh
TORRENT_LIB=/path/to/torrents go run .
```

Переменные окружения:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PORT` | `8000` | порт HTTP, слушает на `0.0.0.0` |
| `TORRENT_LIB` | каталог файла из аргумента | библиотека: где лежат `.torrent` и `.tms-active` |
| `SUBS_DIR` | `<TORRENT_LIB>/subs` | пак субтитров отдельными файлами (см. ниже) |
| `TORRENT_STORE` | `<tmpdir>/webtorrent` | куда качаются куски торрента |
| `TMPDIR` | системный | куда складываются сегменты HLS (`tms-hls-*`) |
| `PROBE_TIMEOUT_MS` | `25000` | сколько ждать ffprobe, прежде чем убить его |
| `HLS_ALLOW_COPY` | вкл. | `0` — всегда перекодировать, не копировать дорожки |
| `TORRENT_PORT` | `42069` | порт для входящих пиров |
| `TORRENT_SEED` | выкл. | `1` — раздавать скачанное |
| `TORRENT_STORE_PERSIST` | выкл. | `1` — не стирать хранилище при остановке |
| `TORRENT_WARMUP_KB` | `256` | сколько прочитать при старте, чтобы поднять рой; `0` — не разогревать |

`TORRENT_PORT` стоит отдельной строкой не зря: значение по умолчанию у библиотеки
фиксированное, поэтому второй экземпляр на той же машине не стартует вовсе —
падает с `bind: address already in use`. При параллельном запуске двух серверов
(например, на время переезда) порт надо развести руками.

Рабочие каталоги: торрент качается в `TORRENT_STORE`, сегменты HLS — в
`<TMPDIR>/tms-hls-<id>`. Оба чистятся сами: сеанс удаляется через 2 минуты после
остановки или замены, стор торрента — при завершении процесса (SIGINT/SIGTERM);
при выходе удаляются и каталоги HLS.

Стирание стора унаследовано от Node (`destroyStoreOnDestroy: true`) и по
умолчанию сохранено, но на проде оно означало бы повторную закачку сериала
при каждом деплое, поэтому в `deploy/compose.yaml` стоит
`TORRENT_STORE_PERSIST=1`. Наружу это никак не наблюдаемо.

**Разогрев роя.** Пиры подключаются только при спросе: куски имеют приоритет
`None`, и пока нет живого читателя, клиент никого не ищет. Поэтому сразу после
перезапуска сервер был бы формально готов, но фактически бесполезен — первый же
`/api/probe` упирался в `ffprobe timed out`, а сеанс умирал в `state=error`.
Теперь при старте читается `TORRENT_WARMUP_KB` килобайт, и флаг готовности
снимается ТОЛЬКО после этого: пока рой холодный, `/api/status` отдаёт
`{"ready":false}`, а телевизор показывает «Torrent metadata loading…»
и спокойно ждёт. Цена — около 20 секунд к старту.

Уже начатый просмотр это не задевает: его сегменты лежат на диске, и подобранный
сеанс отдаётся без участия торрента.

**Субтитры отдельными файлами.** Раздача сериала и перевод к нему почти никогда
не приезжают вместе: в mkv лежат английские дорожки, а русские субтитры
существуют паком из `.srt`. Такой пак кладётся в `SUBS_DIR` — и его дорожки
появляются в меню рядом со встроенными, выбираются и переключаются точно так же.

Связь с сериями только по имени файла без расширения, без учёта регистра:
`s01e01 - The Pilot.srt` в любом подкаталоге найдётся для
`s01e01 - The Pilot.mkv`. Ничего умнее (разбор номеров серий) намеренно нет —
пак, разложенный не один в один, лучше не угадывать.

Язык берётся из названий каталогов (`rus/`, `Russian/`, `frnds_sub_rus_s01-s10/`)
или из суффикса имени файла (`эпизод.rus.srt`); имя серии в опознании
не участвует, иначе «The One Where Joey Speaks English» объявила бы себя
английскими субтитрами. Не опознан — код `und` и подпись «External subtitles».
Кодировка определяется сама: UTF-8 (с BOM или без), иначе CP1251 — половина
русских паков до сих пор приезжает такой.

Каталог перечитывается раз в полминуты, так что пак можно залить на работающий
сервер. Оговорка: разбор серии кэшируется, поэтому дорожка к УЖЕ открытой серии
появится только после перезапуска.

В образе есть самопроверка для `HEALTHCHECK`: `server -healthcheck` бьёт
в `/api/status` на локальный порт и возвращает код возврата. Отдельный флаг
вместо curl — чтобы не тащить в рантайм лишний пакет ради одного запроса.

## API

| Эндпоинт | Что делает |
|---|---|
| `GET /` | встроенный веб-клиент (HTML) |
| `GET /api/torrents` | библиотека: `active` (id или `null`) и список записей |
| `POST /api/torrents` | загрузить `.torrent` — телом запроса или полем формы `torrent` |
| `POST /api/torrents/:id/activate` | сделать торрент активным (гасит текущий сеанс) |
| `POST /api/torrents/:id/delete[?data=1]` | убрать из библиотеки; `data=1` — стереть и скачанное |
| `GET /api/files` | имя торрента и список видеофайлов: `index`, `name`, `length` |
| `GET /api/status` | пиры, скорость, прогресс торрента и снимок текущего воспроизведения |
| `GET /api/probe/:index` | ffprobe файла: видеопоток, аудиодорожки, субтитры (кэшируется) |
| `GET /api/prebuffer/:index` | подтянуть первые 8 МБ файла, чтобы старт был быстрее |
| `GET /api/start/:index?audio=&sub=&start=` | запустить сеанс HLS, вернуть его снимок |
| `GET /api/hls-status/:id` | снимок сеанса: `state`, число сегментов, ошибка ffmpeg |
| `GET /api/stop` | остановить активный сеанс |
| `GET /hls/:id/:file` | плейлисты и сегменты сеанса (`.m3u8`, `.ts`, `.vtt`) |
| `GET /raw/:index` | файл из торрента напрямую, с поддержкой Range; сюда же смотрит ffmpeg |

Серии в `/api/files` отсортированы по пути внутри торрента (числа сравниваются
числами, поэтому «Сезон 2» идёт до «Сезон 10»), а не в порядке метаинформации:
уложить файлы в паке могут как угодно, например по убыванию размера. `index` —
по-прежнему номер файла В ТОРРЕНТЕ, и от сортировки он не зависит: по нему
телевизор хранит позиции просмотра, а сервер ищет файл для `/raw` и `/api/start`.
Тем же порядком считаются `next`/`prev` в `/api/probe`, то есть автопереход.

`audio` и `sub` — код языка (`rus`, `eng`, …) или `off` для субтитров, `start` —
секунды с начала файла. Коды уникальны в пределах файла: вторая дорожка того же
языка получает суффикс (`rus`, `rus-2`), иначе выбрать её было бы невозможно.
Снимок сеанса содержит `playlist` и `subtitlePlaylist`: первый идёт в AVPlay,
второй клиент читает сам и рисует субтитры поверх видео, плюс `videoMode`
и `audioMode` (`copy`/`transcode`/`none`) — что именно делает ffmpeg.

Состояния сеанса: `preparing` → `buffering` (есть первый сегмент) → `ready`
(есть два) → `finished`; `stopped`/`replaced`, если сеанс остановили или
заменили новым, и `error` с хвостом лога ffmpeg. Клиент начинает играть на
`ready` или `finished` и прекращает ждать на остальных.

### Библиотека торрентов

Библиотека — это каталог с `.torrent`-файлами, а не отдельная база: список
строится сканированием `TORRENT_LIB`, загрузка кладёт туда ещё один файл,
выбор активного лежит рядом в `.tms-active`. Всё, что делает страница, можно
повторить руками с сервера — положить файл в каталог или удалить его.

- `id` записи — infohash: тот же торрент, загруженный дважды, остаётся одной
  записью, а имя файла делается из имени раздачи (и чистится от разделителей).
- Переключение сначала гасит ffmpeg, потом поднимает новый источник — и только
  при успехе закрывает прежний. Неудачное переключение оставляет активным то,
  что работало.
- Скачанное при переключении не трогается: хранилище общее на всю библиотеку.
  Удаление торрента по умолчанию тоже оставляет данные; стереть их можно явным
  `?data=1`.
- Загрузка не переключает активный торрент — кроме случая, когда активного нет
  вовсе (тогда включать нечего и прерывать нечего).
- Пока активного торрента нет, сервер отвечает ровно так же, как при незагруженных
  метаданных: `/api/status` → `{"ready":false}`, `/api/files` → 503. Телевизор
  об этом состоянии не знает и знать не должен.

Своей авторизации у загрузки нет — её нет у сервера вообще, наружу он выставляется
reverse-proxy с токеном в пути. Ограничен только размер файла: 4 МБ.

Примеры:

```sh
curl -X POST --data-binary @series.torrent http://127.0.0.1:8000/api/torrents
curl -s http://127.0.0.1:8000/api/torrents
curl -X POST http://127.0.0.1:8000/api/torrents/<infohash>/activate
```

## Почему так

- **MPEG-TS, а не fMP4.** Стриминговый движок телевизоров 2015 года умеет HLS v3;
  fragmented MP4 для него слишком новый.
- **Нормализуем в H.264 high@4.0 + yuv420p + AAC stereo — но только если надо.**
  Прямой ремукс чего угодно ловит форматы, которых декодер не понимает, поэтому
  копируется дорожка лишь при точном попадании в этот же профиль: H.264
  ≤ High/≤ level 4.1, yuv420p, прогрессивная, не больше 1080p; звук — AAC-LC
  до двух каналов на 44.1/48 кГц. Всё остальное идёт через libx264. Копирование
  выключается через `HLS_ALLOW_COPY=0`, если телевизор всё-таки споткнётся.
- **При перемотке копирования нет.** Output-side `-ss` режет поток не по
  ключевому кадру, а расставить свои ключевые кадры в копии нельзя — продолжение
  с середины всегда перекодируется.
- **В режиме copy сегменты неровные.** `-hls_time 4` для копии — нижняя граница:
  ffmpeg режет по тем ключевым кадрам, что уже есть в файле. При длинном GOP
  первые два сегмента могут содержать больше 8 секунд, то есть на старт
  потребуется больше скачанного, чем при перекодировании.
- **Субтитры отдельной дорожкой WebVTT, а не вжигаются фильтром `subtitles=`.**
  Фильтр открывает файл второй раз и читает субтитры до конца, а значит торрент
  скачался бы почти целиком до первого сегмента видео.
- **`-ss` стоит после `-i`** (output-side seek): так тайминги встроенных субтитров
  не разъезжаются при перемотке и продолжении с середины.
- **Субтитры из `SUBS_DIR` собираются в WebVTT сервером, а не ffmpeg.** Вторым
  входом их не подсунуть: при output-side `-ss` ffmpeg выбрасывает реплики
  раньше `start`, но оставшимся время НЕ пересчитывает — видео едет с нуля,
  а реплика 30-й секунды остаётся на 30-й. Переставить `-ss` нельзя, на нём
  держится строчка выше. Побочно вышло лучше: текст готов ещё до первого
  сегмента и переживает выкатку вместе с каталогом сеанса.
- **Активный сеанс всегда один.** Новый `/api/start` убивает предыдущий ffmpeg —
  два перекодирования одновременно ни торрент, ни процессор не выдержат.
- **Клиент получает медиаплейлист, а не мастер.** Tizen 2.3 не разбирает
  `#EXT-X-MEDIA`, поэтому дорожку субтитров приложение забирает само.
- **Плейлист объявлен как `EVENT` и просит начинать с нуля.** Обычный живой
  плейлист плеер открывает не с начала, а за три `TARGETDURATION` от конца —
  и серия начиналась с 00:15–00:35, потому что ffmpeg в режиме copy успевает
  нарезать минуту, пока телевизор доходит до плейлиста. Поэтому в аргументах
  есть `-hls_playlist_type event`, а сервер дописывает на отдаче
  `#EXT-X-START:TIME-OFFSET=0` (у ffmpeg такой опции нет).

В прод сервер публикуется через внешний reverse-proxy (в `DEFAULT_SERVER` клиента
адрес с токеном в пути) — конфигурации прокси в этом репозитории нет.
