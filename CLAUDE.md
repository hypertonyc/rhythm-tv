# CLAUDE.md

Rhythm TV — медиасервер и клиент к нему для Samsung Smart TV на Tizen 2.3
(телевизоры 2015 года). Пользовательское описание в [README.md](README.md),
[client/README.md](client/README.md) и [server/README.md](server/README.md);
здесь то, что нужно знать перед правкой кода.

## Раскладка репозитория

```
client/     приложение для телевизора: index.html, js/app.js, css/, config.xml,
            tizen_web_project.yaml, .tproject
server/     сервер на Go: main.go, internal/*, Dockerfile
            legacy/server.mjs — прежний сервер на Node, теперь эталон для сверки
scripts/    tizen-build-install.sh — сборка, подпись и установка на телевизор
            compat-node-vs-go.sh — сверка Go-сервера с Node-эталоном
data/       .torrent-файлы, в .gitignore
.vscode/    задача, которая вызывает скрипт сборки клиента
.env        локальные настройки сборки, в .gitignore (шаблон — .env.example)
```

Две половины связаны только по HTTP: клиент дёргает эндпоинты сервера
(список в [server/README.md](server/README.md)). Меняя формат ответа на сервере,
надо править и `client/js/app.js` — общего кода и типов нет.

Обе истории лежат в одном репозитории: сервер приехал subtree-мержем из бывшего
`torrent-media-server`, его коммиты видны в графе до слияния.

## Клиент (`client/`)

**`client/js/app.js` — строго ES5.** WRT на Tizen 2.3 не понимает `let`/`const`,
стрелочные функции, шаблонные строки, `Promise`, `async`/`await`, `fetch`,
деструктуризацию, `Array.prototype.includes`. Только `var`, `function`,
`XMLHttpRequest`, колбэки. Это не стилевое предпочтение — код просто не запустится.
Предупреждение стоит в шапке файла. К серверу это не относится: он на Go.

**Никакой сборки.** Нет npm, package.json, бандлера, транспайлера, тестов, линтера.
Клиент — это набор статических файлов, который упаковывается в `.wgt`.
Не предлагать TypeScript, модули ES, зависимости из npm.

**Новый файл надо вписать в `files:` в `client/tizen_web_project.yaml`,** иначе он
не попадёт в пакет, и приложение на телевизоре молча сломается. Скрипт сборки
проверяет наличие `js/app.js` и `js/config.js` в готовом `.wgt` именно из-за
этой грабли.

**На телевизоре нет консоли.** Отладка только через экран: `window.onerror` пишет
в красный блок `#fatal`, для сообщений по ходу работы есть `showHud()` в плеере
и `setStatus()` в меню. Быстрая альтернатива — открыть `/` на сервере: там тот же
плеер в браузере, с нормальным devtools.

### Как устроен app.js

Один IIFE, состояние в переменных модуля. Экран определяется переменной `mode`
(`'boot'` → `'setup'` / `'menu'` / `'player'`), переключение — присваиванием `className`
контейнерам из `index.html`. Вся навигация с пульта в `handleKey()`, коды кнопок
берутся через `tizen.tvinputdevice.getKey()` с числовыми фолбэками.

Неочевидные решения, которые выглядят как мусор, но нужны:

- **`guardedRequest()`** — обёртка над XHR со сторожевым таймером. На этом WRT запрос,
  отклонённый WARP, может не вызвать ни `onerror`, ни `ontimeout`, и колбэк не придёт никогда.
- **Тройной запуск `bootOnce()`** — `DOMContentLoaded`, `window.onload` и `setTimeout` на 2 с.
  `window.onload` срабатывает не на всех сборках Tizen, если в документе есть объект avplayer.
  Флаг `booted` защищает от повторного входа.
- **Субтитры рисуются на `<canvas>`,** а не отдаются AVPlay. Текст берётся из отдельного
  VTT-плейлиста (`subtitlePlaylist` из ответа сервера), который опрашивается по XHR раз
  в 1200 мс (`pollSubtitlePlaylist`), парсится вручную (`parseVtt`) и выводится
  в `drawSubtitle`. Через TEXT-трек AVPlay на старом компоновщике субтитры
  не показывались — путь с треком уже пробовали и убрали.
- **Перемотки как таковой нет.** `seekRelative()` закрывает AVPlay и заново запускает HLS
  с сервера с новым `start=`. `avplay.seekTo` на этой прошивке ненадёжен.
- **Пустые `onevent`/`onsubtitlechange`** в листенере AVPlay оставлены сознательно —
  на старых прошивках неполный объект листенера приводит к ошибкам.

### Адрес сервера

В коде адрес не хардкодится. `DEFAULT_SERVER` лежит в `.env`, скрипт сборки генерирует
из него `client/js/config.js` с `window.RTV_CONFIG.defaultServer`, а `app.js` читает
оттуда с фолбэком на пустую строку (пустая = откроется экран настройки).
`client/js/config.js` в `.gitignore`, потому что адрес содержит приватный токен в пути.

Сохранённый пользователем адрес в `localStorage` (`rtv.server`) имеет приоритет над
запечённым — если меняли адрес на телевизоре, новая сборка сама его не подхватит.

Ключи в localStorage: `rtv.server`, `rtv.positions` (JSON: индекс файла → секунды),
`rtv.lastEpisode`, `rtv.audio`, `rtv.sub`, `rtv.autonext`, `rtv.subtitleSize`.

## Сервер (`server/`)

Go 1.26, из зависимостей `github.com/anacrolix/torrent`; ffmpeg и ffprobe
вызываются как процессы. Запуск: `go run . /path/file.torrent`, порт из `PORT`
(8000). Один процесс — один торрент, один активный сеанс перекодирования.

Пакеты разрезаны **по опасности, а не по существительным**:

```
main.go                      конфиг из окружения, проводка, сигналы, shutdown
internal/jscompat/           всё, где Go ведёт себя иначе, чем JS (см. ниже)
internal/mediasource/        anacrolix за интерфейсом Source + Fake для тестов
internal/media/              ffprobe, выбор дорожек, правила копирования
internal/hls/                сеанс ffmpeg: аргументы, монитор, остановка
internal/httpapi/            роутер и обработчики; web/index.html — go:embed
```

`jscompat` существует не ради чистоты: контракт с телевизором заморожен
байт-в-байт, а Tizen ловит расхождения молча — приложение просто гаснет.
Всё, что зависит от семантики JS, лежит там и там же покрыто тестами.
`mediasource` — чтобы anacrolix был подменяем, а тесты шли без роя.

**Места, где приколота одноторрентность,** помечены комментарием
`// MULTI-TORRENT PIN:` — их четыре, и все меняются аддитивно.

### Как это проверяется

Контракт заморожен, поэтому проверка идёт не «по ожиданиям автора», а сверкой
с Node-эталоном в `server/legacy/`:

- **Golden-файлы в `testdata/`** сняты запуском кода, вырезанного ИЗ `server.mjs`
  построчно (`sed -n '271,314p'` и т.п.), а не переписанного руками. Рядом лежат
  скрипты-генераторы `replay-*.mjs`. Так покрыты argv ffmpeg (8 сценариев),
  разбор ffprobe и порт `throughput` для `downloadSpeed`.
- **`./scripts/compat-node-vs-go.sh data/tbbt.torrent`** поднимает оба сервера
  на одном торренте и сравнивает настоящие HTTP-ответы: статус, заголовки и тело.
  Живые счётчики (`/api/status`) сравниваются по форме — каждое листовое значение
  заменяется своим типом с сохранением порядка ключей.

`node` в системе не установлен, эталон гоняется через Docker.

Неочевидные решения (подробнее в [server/README.md](server/README.md) и комментариях):

- **Субтитры не вжигаются в видео.** Фильтр `subtitles=` открыл бы файл второй раз
  и дочитал субтитры до EOF — торрент скачался бы почти целиком до первого сегмента.
  Вместо этого выбранная дорожка мапится и отдаётся отдельной WebVTT-дорожкой HLS.
- **Клиентам отдаётся `index.m3u8`, а не мастер-плейлист** — Tizen 2.3 не понимает
  `#EXT-X-MEDIA`. `master.m3u8` появляется как побочный эффект `-var_stream_map`
  и не используется ни телевизором, ни браузерным клиентом.
- **`-ss` после `-i`** (output-side seek) — иначе разъезжаются тайминги встроенных
  субтитров при продолжении с середины.
- **Целевой формат — H.264 high@4.0 + yuv420p + AAC stereo, MPEG-TS.** Если исходник
  уже точно такой (`canCopyVideo`/`canCopyAudio`: h264 ≤High/≤4.1, yuv420p,
  прогрессивный, ≤1080p; AAC-LC ≤2 канала 44.1/48 кГц) и `start` равен нулю —
  дорожка копируется без перекодирования. Всё прочее идёт через libx264: ремукс
  чего угодно ловит форматы, которых декодер 2015 года не понимает.
  `HLS_ALLOW_COPY=0` возвращает безусловное перекодирование.
- **Ключевой кадр раз в 4 с** (`-force_key_frames`) при `-hls_time 4`, чтобы сегменты
  резались ровно. В режиме copy этого рычага нет — режется по тому, что есть в файле.
- **Новый `/api/start` убивает предыдущий ffmpeg** (причина `replaced`) и планирует
  чистку каталога через 2 минуты — клиент может ещё дотягивать сегменты.
- **Ничего не качается само.** У anacrolix куски по умолчанию имеют приоритет
  `PiecePriorityNone`, и `DownloadAll()` не вызывается — это и есть аналог
  webtorrent-овского `deselect: true`. Данные тянет только живой `Reader`,
  то есть чтение через `/raw/:index` и префетч (первые 8 МБ).
  **Каждый `Reader` обязан быть закрыт:** пока он жив, вокруг его позиции держится
  окно приоритета, и торрент качается уже после ухода клиента.
- **Готовность считается по файлам на диске, инкрементально:** `pollSegments()` идёт
  по номерам сегментов и считает только новые (`-hls_flags temp_file` делает
  появление файла атомарным), а снимок сеанса — чистая функция над готовыми
  счётчиками. Фаза живёт в `session.phase` (`preparing` → `buffering` (1)
  → `ready` (≥2) → `finished`), причина остановки — отдельно в `stopReason`;
  наружу они сводятся в одно поле `state`. Клиент стартует на `ready`/`finished`
  и прекращает ждать на `stopped`/`replaced`/`error`.
- **Всё состояние сеансов под одним мьютексом `Manager.mu`.** Node был безопасен
  event loop'ом; в Go эта сериализация восстановлена явно. Один лок на всё убирает
  порядок блокировок как класс, а нагрузка тут — тик раз в 500 мс. Горутина,
  ждущая выхода ffmpeg, перед записью итогов **дожидается `monitorDone`**: без
  этого рандеву последний тик монитора мог бы уехать после записи.
- **Логи anacrolix отфильтрованы** (`internal/mediasource/logging.go`). Он пишет ERR
  на каждое отменённое чтение, а отменяем его мы сами: ffmpeg рвёт ответ и заходит
  новым Range при каждой перемотке — это три строки ERR на обрыв. Фильтров два,
  потому что в библиотеке два пути логирования: свой `alog` и стандартный `slog`;
  сообщения ридера идут через второй.

Веб-клиент (`internal/httpapi/web/index.html`, вшит через `go:embed`) — второй
потребитель того же API. Меняя формат ответов, проверять оба: телевизор и браузер.
Файл обязан оставаться **без завершающего перевода строки**: по нему считается
`Content-Length`, а редактор добавляет `\n` молча. Это проверяется тестом.

### Где Go расходится с JS

Полный список — в комментариях `internal/jscompat/`, здесь то, что кусается чаще:

- **`encoding/json` экранирует `<`, `>`, `&`**, а `JSON.stringify` — нет, и
  `Encoder.Encode` дописывает `\n`. Оба расхождения бьют по `Content-Length`
  на каждом ответе. Поэтому в коде везде `jscompat.Marshal`, а не `json.Marshal`.
- **Пустой слайс маршалится в `null`.** Клиент читает `meta.audio.length` без
  проверки — `null.length` гасит всё приложение через `window.onerror`.
  Слайсы создавать через `make([]T, 0)`.
- **Поля, которые бывают null, — только указателями.** Клиент сравнивает
  `meta.next === null` строго: отсутствующий ключ даст `undefined`, сравнение
  не пройдёт, и автопереход сработает на последней серии.
- **`\s` в JS шире, чем в Go**, и включает NBSP. Заголовок дорожки с NBSP
  (обычное дело в рипах) дал бы другой label → другой суффикс дизамбигуации →
  другой code, а телевизор хранит выбранную дорожку в localStorage именно как code.
  `strings.TrimSpace` тоже не годится: у него свой третий набор.
- **`toFixed` округляет половины вверх, `strconv.FormatFloat` — к чётному.**
- **`r.URL.EscapedPath()`, не `Path`**, и никакого `http.ServeMux`: он чистит путь
  и отвечает 301 там, где оригинал отдавал 404.
- **`ProcessState.ExitCode()` даёт -1 для убитого сигналом**, а Node давал `null`.
  Без перевода убитый по SIGKILL сеанс ложно попадал бы в состояние `error`.
- **Литеральный U+FEFF в исходнике Go — ошибка компиляции** («illegal byte order
  mark»), а NBSP и U+212A в коде неотличимы от обычных символов. В тестах все
  невидимые символы записаны escape-ами, иначе следующая правка обнулит кейс.

## Сборка и запуск

Клиент: `./scripts/tizen-build-install.sh` (или задача `Tizen: Build & Install on TV`
в VS Code, которая его и вызывает). Порядок: проверка `.env` → генерация
`client/js/config.js` → `sdb connect` → `rm -rf client/Debug/` → `tz build` → `tz pack`
→ проверки содержимого `.wgt` (подпись, `js/app.js`, `js/config.js`) → `tizen install`.
Версия приложения живёт в `client/config.xml` (атрибут `version` у `<widget>`).
`client/Debug/` — целиком результат сборки, пересоздаётся каждый раз, в `.gitignore`.

`tz pack` называет пакет по каталогу проекта (`client.wgt`), `output_name`
в `tizen_web_project.yaml` он игнорирует. На телевизор это не влияет: id и package
приложения берутся из `config.xml` (`IDwM3cpKkk.torrentmediaclient`).

### Обёртка над sdb

**`sdb` в тулчейне — не оригинал, а наш bash-скрипт;** оригинальный бинарник лежит
рядом как `sdb.real`. Копия обёртки — [scripts/sdb-wrapper.sh](scripts/sdb-wrapper.sh),
она же и ставится: `./scripts/sdb-wrapper.sh --install` (путь берёт из `SDB` в `.env`,
повторный запуск безопасен). Восстанавливать приходится потому, что тулчейн живёт вне
репозитория (`~/.tizen-extension-platform/server/sdktools/`) и переустановка SDK
затирает обёртку оригинальным `sdb`.

Обёртка делает три вещи:

- пишет все вызовы sdb в `/tmp/tizen-vscode-sdb.log` — единственный способ увидеть,
  что именно делает с телевизором расширение VS Code;
- `vd_applist` → `applist`;
- переписывает путь `.wgt` из корня в `/opt/usr/apps/tmp`: на сетах 2015 года корень
  read-only, `tz install` кладёт пакет в `/`, push падает с «failed to close»,
  и `vd_appinstall` потом ничего не находит.

Последние два фикса нужны только установке через `tz` (сборка из UI расширения).
`scripts/tizen-build-install.sh` ставит Java-шным `tizen`, который сам пишет
в `/opt/usr/apps/tmp`, — на этом пути фиксы не срабатывают, но логирование работает.

Сервер: `docker build` + `docker run` из `server/` (см. README) либо
`go run . file.torrent` при локально установленном ffmpeg.

## CI и деплой

Подробности и ручные шаги настройки — в [deploy/README.md](deploy/README.md),
здесь то, что нужно знать, правя пайплайн.

| Файл | Когда срабатывает |
|---|---|
| `.github/workflows/server.yml` | `server/**`, `deploy/**` → тесты, образ в GHCR, затем деплой |
| `.github/workflows/deploy.yml` | вызывается из server.yml; отдельно — для отката |
| `.github/workflows/client.yml` | `client/**`, `scripts/**` → проверки ES5 и манифеста |
| `.github/workflows/secrets.yml` | всегда → скан на токен и прод-хост |

Неочевидное:

- **Сборка и деплой — разные файлы,** потому что откат не должен требовать
  пересборки. `deploy.yml` принимает тег образа входным параметром, так что
  откатиться — это один `gh workflow run`, а не повторный прогон вчерашней сборки.
- **Деплой ставится в очередь и не отменяется** (`cancel-in-progress: false`):
  отмена между подменой `.env` и `up -d` оставила бы `/srv/tms` описывающим
  не тот образ, который запущен.
- **Перед выкаткой пайплайн спрашивает сервер, не смотрит ли кто-то серию.**
  Редеплой убивает живой ffmpeg, а всё состояние сеанса лежит в процессе —
  настоящий zero-downtime тут недостижим и не нужен. Если смотрят, деплой падает;
  образ уже в GHCR, так что ничего не потеряно. Обойти — `force=true`.
- **`compose.yaml` едет на VPS по stdin,** а не лежит там: `scp` под forced
  command невозможен, а stdin работает. Ключ CI умеет ровно четыре глагола
  (`deploy`/`rollback`/`status`/`playback`), см. [deploy/tms-deploy](deploy/tms-deploy).
- **Токен прокси в CI не попадает и не должен:** дымовой тест бьёт в
  `127.0.0.1:8000` изнутри VPS. Переделывать его во внешнюю проверку нельзя.
- **Образ помечается голым sha коммита,** и деплоится только он. `latest` —
  для рук. Чистку версий в GHCR включать нельзя: она удалит цели отката.
- **`shellcheck` в CI падает и на предупреждениях.** `SC1091` исключён
  осознанно: скрипт сборки делает `source .env`, а `.env` в `.gitignore`.

Локальный `pre-commit`-хук стоит завести парой к `secrets.yml` — тот срабатывает
уже после пуша (`/usr/bin/grep`, потому что обёртка в этой оболочке пропускает
gitignored пути):

```sh
# .git/hooks/pre-commit, chmod +x
if git diff --cached -U0 | /usr/bin/grep -qE '^\+.*[0-9a-f]{40,}'; then
  echo 'ЗАБЛОКИРОВАНО: 40+ hex-символов в staged diff (токен прокси — 48)'; exit 1
fi
```

## Окружение

`node` и `npm` в системе не установлены — сервер здесь не запустить, только читать
и править код. Синтаксис клиентского JS можно проверить через JavaScriptCore:

```sh
/System/Library/Frameworks/JavaScriptCore.framework/Versions/A/Helpers/jsc \
  -e "new Function(readFile('client/js/app.js')); print('OK')"
```

Полную сборку клиента без подключённого телевизора прогнать нельзя — скрипт падает
на проверке `sdb devices`.

`grep` в этой оболочке — функция-обёртка, которая пропускает gitignored и скрытые пути.
Для проверок, где важна полнота (скан `.git`, поиск в `client/js/config.js` или `.env`),
нужен `/usr/bin/grep`, иначе результат «ничего не найдено» ничего не значит.

## Открытые вопросы

- `waitForHls()` в клиенте опрашивает сервер каждые 700 мс без предела попыток: если
  сегменты так и не появятся, опрос будет идти бесконечно (решено оставить так).
- Сервер не ограничивает размер `<tmpdir>/tms-hls-*`: длинный эпизод перекодируется
  целиком и лежит на диске до остановки сеанса. При выходе процесса каталоги удаляются.
